Getting started

The example used in this guide

Every screenshot and number comes from one small web shop and one test plan, so you can repeat each step yourself.

The shop

demo-server.py is a tiny web server that listens on 127.0.0.1:8089. It needs only Python 3.

AddressWhat it does
GET /Returns a page with a hidden form field named csrf. Its value is new on every request.
POST /loginReturns JSON such as {"token": "9f2c…"}. The token is new on every call.
GET /cart?token=…Answers 200 only if the token was issued by /login. Otherwise 401.
GET /slowWaits about 300 ms before answering.
GET /failAlways answers 500, so every run has a known share of errors.

The plan

shop-demo.jmx has one thread group named Shoppers with 10 users, a 5 second ramp-up and 10 loops. Each loop calls five requests:

  1. Home page checks that the page contains the csrf field, and a Regular Expression Extractor saves its value as ${csrf}.
  2. Log in posts a JSON body. A JSON Extractor saves $.token as ${token}.
  3. View cart sends ${token} back to the server.
  4. Slow report and Broken page give the results something to show.

A run makes 500 requests. We expect 100 errors (20%), all from the broken page, and no errors from the cart. If the cart fails, correlation is not working.

Try it yourself

  1. Start the shop 
    python docs/guide/demo/demo-server.py 8089
  2. Run the plan without a window 
    jmeter -n -t docs/guide/demo/shop-demo.jmx -l results.jtl -e -o report

    You should see Err: 100 (20.00%) at the end.

  3. Open the plan in a window. Use Apache JMeter (jmeter -t docs/guide/demo/shop-demo.jmx) or our app (cargo run -p jmeter-ui -- docs/guide/demo/shop-demo.jmx).
Warning

Only point load tests at systems you own or have permission to test. This example listens on your own machine only.

Performance testing

Types of performance tests

"Performance test" is a family of tests. Each one asks a different question, so each needs a different load shape.

Note

Names vary between teams. Some call soak tests "endurance" tests, and stress and breakpoint tests overlap. What matters is the question you are asking. The descriptions below follow the common definitions in the sources.

The main types

TypeQuestion it answersLoad shapeWhat you look for
SmokeDoes the script and the environment work at all?One or a few users, one loop.No errors. Correct responses.
LoadDoes the system meet its targets under the load we expect?Ramp up to the expected number of users, hold, ramp down.Response-time percentiles, error rate and throughput against your targets.
StressWhat happens beyond normal capacity, and does it recover?Push past expected load until things break, then reduce it.Where errors start, how it fails, how fast it recovers.
SpikeCan it survive a sudden surge, such as a sale or a launch?Jump from low load to very high load in seconds, then drop.Errors during the jump and recovery time afterwards.
Soak (endurance)Does it stay healthy over hours?Expected load, held for hours.Slow memory growth, leaked connections, response times that creep up.
ScalabilityHow does performance change as load or resources grow?Step the load up (or add servers) in stages.Whether throughput grows in step with the load or flattens.
Volume (data)Does it cope with large amounts of data?Normal load against a very large database or file set.Query times, storage and batch durations.
Breakpoint (capacity)What is the most it can handle while still meeting targets?Increase load step by step until the first target is missed.The highest load that still passes.

How these look in JMeter

JMeter makes the load shape from a few settings on the Thread Group:

  • Number of threads is the number of virtual users.
  • Ramp-up period is the time over which users are started.
  • Loop count or Duration sets how long each user keeps going.

A smoke test is one thread and one loop. A soak test is a moderate thread count with a duration of hours. Spike and stepped tests need more than one thread group, or a plugin that shapes the load over time. Throughput can be held at a target with a timer such as the Constant Throughput Timer.

Performance testing

Where performance tests fit in development

The cheapest time to find a slow page is while it is being built. The most reassuring time is just before release. Most teams do some of each.

By phase of the project

PhasePerformance workTypical tests
RequirementsAgree numbers that mean "fast enough": for example 95% of searches under 800 ms, fewer than 1% errors, 200 orders per minute.None yet. Write the targets down.
DesignEstimate capacity. Pick likely bottlenecks to check first.None yet. Plan the tests.
DevelopmentCheck each service or page as it is built. Catch slow queries early.Smoke tests of single requests or small flows, run by developers.
Integration and QABuild the real scripts. Measure a baseline. Compare every build with it.Load tests, regression tests against the baseline.
Pre-release (staging)Prove the system with production-like data and hardware.Load, stress, spike, soak, scalability, volume.
ReleaseWatch real traffic. Run light, safe checks against production.Smoke tests. Careful, small-scale checks.
OperationsRe-test after big changes, before busy seasons, and when capacity changes.Load, spike, breakpoint.
Tip

Run a small smoke test on every change and the larger tests on a schedule or before releases. A one-minute test that runs every time catches more problems than a two-hour test that nobody runs.

The numbers that matter

MeasureWhat it tells you
Response time (average)The typical time for a request. One slow request can hide inside an average.
Percentiles (90th, 95th, 99th)The time that 90, 95 or 99 percent of requests beat. This shows what the slowest users see.
ThroughputRequests completed per second.
Error rateThe share of requests that failed, including failed checks.
APDEXA single score from 0 to 1 that counts requests as satisfied, tolerating or frustrated, using two time limits.
Concurrent usersHow many virtual users are active at the same moment.

Using JMeter

Record a script

Instead of typing every request by hand, point a browser at JMeter and let it write the requests while you click through the site.

How it works

JMeter starts a proxy on your machine. Your browser sends its traffic through the proxy, and JMeter turns every request it sees into an HTTP Request in your plan. For HTTPS sites, JMeter makes a temporary certificate authority that the browser must trust.

Record a site in JMeter

  1. Start from the Recording template. Choose File > Templates… and pick Recording, or Recording with Think Time. The template adds a thread group, a Recording Controller and the recorder.
  2. Or add the recorder yourself. Right-click the Test Plan and choose Add > Non-Test Elements > HTTP(S) Test Script Recorder.
  3. Choose where the requests go. Set Target Controller to the Recording Controller, and decide how to group requests. Leave the port at 8888 unless something else uses it.
  4. Filter out the noise. On the Requests Filtering tab, exclude images, style sheets and scripts so only the calls you care about are recorded.
  5. Click Start. JMeter creates ApacheJMeterTemporaryRootCA.crt in its bin folder. Import that file into your browser as a trusted authority. It expires after a few days, on purpose.
  6. Point the browser at the proxy. In the browser's network settings, use a manual proxy of localhost on port 8888.
  7. Click through the journey. Do what a real user does. Requests appear under the Recording Controller as you go.
  8. Click Stop, then tidy up. Remove requests you do not want, give clear names, add think time, and replace recorded dynamic values with variables. The next task, correlating values, covers that last part.

Other ways to get a first script

  • Import from cURL. Tools > Import from cURL turns a command copied from the browser's developer tools into a request.
  • Templates. Ready-made plans for web, SOAP, FTP, LDAP, JDBC and more.
Tip

Record one short, typical journey rather than a whole session. Short recordings are easier to clean up and to make repeatable.

Build and edit a script

A JMeter script is a tree. The window shows the tree on the left and a form for the selected element on the right.

The parts of a plan

PartWhat it doesExample
Thread GroupSets how many users run, how fast they start and how long they keep going.Shoppers: 10 users, 5 second ramp-up
SamplerSends one request and records the result.HTTP Request to /login
Logic controllerDecides which samplers run, and in what order or how often.Loop, If, Transaction
Config elementSupplies shared settings.HTTP Request Defaults, Cookie Manager, CSV Data Set
TimerAdds a pause, to imitate a person thinking.Constant Timer, 200 ms
Pre- and post-processorPrepares a request or reads a response.JSON Extractor
AssertionChecks a response and fails the request if it is wrong.Response Assertion
ListenerCollects and shows results.Summary Report

Edit a plan in JMeter

  1. Select an element to see its form. The thread group form holds the user count, ramp-up and loop count.
  2. Open a request. An HTTP Request has a method, a path, options and a body. A JSON body goes on the Body Data tab, in an editor with syntax colours.
  3. Add an element. Right-click a node and choose Add. JMeter only offers what fits at that point in the tree.
  4. Rearrange. Drag nodes to move them. Use Ctrl+C, Ctrl+X and Ctrl+V to copy, cut and paste, also between plans. Duplicate makes a copy next to the original.
  5. Turn parts off. Ctrl+T toggles an element. A disabled element stays in the plan but does not run.
  6. Find and replace. Search > Search (Ctrl+F) finds text anywhere in the tree.
  7. Reuse pieces. Save Selection As… saves part of a plan to a file, Merge brings one in, and Save as Test Fragment keeps a reusable block in the plan.
  8. Save. Ctrl+S writes a .jmx file. It is plain XML, so it works well in version control.

The menus

JMeter puts almost everything in its menu bar. Menu comparison lines these up against our app.

Using JMeter

Correlate dynamic values

Many sites hand out values that change on every visit: session tokens, form tokens, order numbers. A recorded script replays the old value and fails. Correlation means capturing the value from one response and sending it in the next request.

The idea

  1. Find the value that changes. Compare two recordings, or look at a failing request.
  2. Add an extractor under the request that returns the value. It saves the value into a variable.
  3. Use the variable, written ${name}, in the later request.

JMeter has no automatic correlation. You choose each value yourself.

Pick an extractor

ExtractorUse it when the response is…Expression example
JSON ExtractorJSON$.token
Regular Expression ExtractorAny text, such as HTML or headersname="csrf" value="(.+?)"
CSS Selector ExtractorHTML you can address by elementinput[name=csrf]
XPath ExtractorXML or well-formed HTML//input[@name='csrf']/@value
Boundary ExtractorText between two fixed stringsLeft value=", right "

Correlate a login token in JMeter

  1. Add a JSON Extractor under the Log in request. Right-click Log in, then Add > Post Processors > JSON Extractor.
  2. Fill in the extractor. Name the variable token, use the path $.token, set the match number to 1, and give a default of NOT_FOUND so a missing value is easy to spot.
  3. Use the variable. In View cart, add a parameter named token with the value ${token}.
  4. Check it. Run the plan with a View Results Tree listener. If View cart returns 200 instead of 401, the correlation works. The tree also has testers for regular expressions and JSON paths.

Make values different for each user

  • CSV Data Set Config reads one line of a file per user or loop, which suits user names and passwords.
  • User Defined Variables hold values you reuse, such as the server name.
  • Functions such as ${__Random(1,100)} and ${__time()} make values on the fly. Tools > Function Helper Dialog builds and tests them.

Using JMeter

Run a test

JMeter can run a plan from its window or from the command line. Use the window to build and check a plan. Use the command line for real load.

Run from the window

  1. Start. Click the green arrow, press Ctrl+R, or choose Run > Start. Start no pauses ignores timers.
  2. Watch. The top right shows elapsed time, warnings, and active and total users (for example 0/10). Open a listener to see results arrive.
  3. Stop. Ctrl+. stops now. Shutdown (Ctrl+,) lets running requests finish first.
  4. Clear. Ctrl+E clears all listeners before the next run.
Warning

The window uses a lot of memory when it draws every result. The JMeter manual recommends running load tests without it.

Run from the command line

jmeter -n -t shop-demo.jmx -l results.jtl -e -o report
OptionMeaning
-nNo window (non-GUI mode)
-tThe plan to run
-lWhere to write the results file
-e -oMake the HTML report in the named folder when the run ends
-J name=valueSet a property, so one plan can run with different users or servers

While it runs, JMeter prints a summary line every 30 seconds with samples, rate, average, minimum, maximum, errors and active users.

Check a plan before a big run

Validate runs the selected thread group with one user and no timers. It is a quick way to see that every request works before you add the load.

Using JMeter

Run a distributed test

One machine can only generate so much load. A distributed test uses several machines, called workers, each running the plan while one controller starts them and collects the results.

How it works

  • Each worker runs a small JMeter server program (jmeter-server).
  • The controller sends the plan to every worker and starts them together.
  • Each worker runs the whole plan. Ten users on three workers means thirty users in total.
  • Workers send results back to the controller.

Set it up

  1. Match versions. Install the same JMeter and Java versions on every machine. Make sure the machines can reach each other through any firewall.
  2. Share the encryption keys. JMeter encrypts traffic between machines. Create the key store with create-rmi-keystore in the bin folder and copy rmi_keystore.jks to every machine.
  3. Start the workers. On each worker, run jmeter-server.
  4. List the workers. On the controller, set remote_hosts in jmeter.properties to the worker addresses, separated by commas.
  5. Copy data files. The plan is sent, but files it reads, such as a CSV of users, must already be on each worker.
  6. Start the test. In the window, choose Run > Remote Start All (Ctrl+Shift+R) or start one worker from Remote Start. From the command line, use -R host1,host2 with -n.
  7. Stop or shut down. Remote Stop, Remote Shutdown and Remote Exit act on one worker or on all of them.
Tip

The controller can become the bottleneck if it must show every result. Run the controller without a window and write results to a file.

Using JMeter

Report on results

JMeter shows results three ways: live in listeners, from a saved results file, and as a shareable HTML report.

Live results in listeners

A listener shows results as they arrive. The three you will use most:

ListenerBest for
Summary ReportOne row per request name with samples, average, minimum, maximum, standard deviation, error rate, throughput and bytes.
Aggregate ReportThe same, plus median and the 90th, 95th and 99th percentiles.
View Results TreeReading one request: what was sent, what came back, and why a check failed.

Save results and load them again

Every listener has a Filename box. Give it a file and the listener writes each result there. The same box, with Browse…, loads a saved file back into the listener, so you can study an old run in a window without running anything. Configure chooses which fields are saved.

The HTML report

The HTML report is a folder of web pages with charts. You can open it in any browser or send it to someone.

  1. Make it during a run. Add -e -o report to the command line.
  2. Or make it from a saved file. Choose Tools > Generate HTML report, pick the results file, an optional user.properties file and an empty output folder. On the command line: 
    jmeter -g results.jtl -o report
  3. Open index.html. The dashboard shows the test details, an APDEX table, a pass and fail chart, a statistics table, the errors, and charts over time.
Note

The results file must be in CSV form with JMeter's usual columns, and the output folder must be new or empty.

Beyond one run

For long tests or many runs, a Backend Listener streams live results to a database such as InfluxDB, which a dashboard tool like Grafana can chart.

Trying our JMeter UI

The same six tasks in our JMeter UI

We repeated each task with the same example plan. This page shows what we saw, with a verdict for each.

Note

Our app edits .jmx files and runs the real JMeter in the background, so the numbers come from the same engine. What differs is the window around it.

1. Record a script

Missing

There is no recorder, no templates and no import from cURL.

We searched the menus and the command palette for record, template, import and function and found nothing. The Tools menu holds only palette commands.

What this means: a new test cannot start from a recording. Users record in Apache JMeter or another tool, then open the file here.

2. Build and edit a script

Partly

Editing is quick and pleasant. Starting and reusing are the gaps.

What worked well

  • Selecting any element shows a clear form with plain-language labels, for example "Number of threads (users)" and "Loop count (-1 for forever)".
  • Adding is fast. Press Ctrl+Shift+P, type +regular and choose the Regular Expression Extractor. It is added under the selected request.
  • Edits are marked as unsaved on the tab, saved with Ctrl+S, and undo and redo work. After we saved, the new extractor was in the file with the values we typed.

What was missing or awkward

  • No File > New. The File menu only opens existing plans. A new plan cannot be started here.
  • No copy, cut or paste of elements, no Merge, no Save Selection As and no Test Fragment.
  • The request body is one line. The JSON body of Log in sits in a table cell, with no multi-line editing and no colours. JMeter has a Body Data tab for this.
  • The palette's add mode is hard to find. Typing json says "No matches". You need to type +json. The hint is in the footer of the box.

3. Correlate dynamic values

Partly

The extractor forms work, and the app warns about unknown variables. You cannot test an expression before running.

We filled in a Regular Expression Extractor (csrf, name="csrf" value="(.+?)", template $1$, match 1, default NOT_FOUND) and saved. The saved file matched what we typed.

Then we set a request path to /slow?x=${nope}, a variable nothing defines. The Problems tab named it straight away:

Strength

Catching a misspelled variable before a run is something JMeter's window does not do. It only shows up as a failed request.

Missing: there is no tester for a regular expression or JSON path against a real response, no Function Helper, and no view of variable values after a run. Correlation is trial and error.

4. Run a test

Works

Press F5 and watch. Our numbers matched JMeter's.

We pressed F5. The results panel opened by itself with six live tiles and four charts, and a status message appeared when the run ended.

MeasureApache JMeterOur JMeter UI
Samples500500
Errors100 (20%)100 (20%)
Average response time80 ms82 ms
Cart requests failing00 (correlation works)

Also in our app:

  • The Run menu has Validate Plan (one user, once) (Ctrl+F5) and Send Selected Request Once (F6), and Stop and Stop now.
  • Every run is saved in its own folder next to the plan, with the results file, the JMeter log and the plan exactly as it ran. The History tab lists them.
  • The run never changes your .jmx file.

5. Run a distributed test

Missing

There is nothing for remote hosts.

There is no place to list workers, no Remote Start or Stop, and no setup for the encryption key store. Distributed runs still have to be started outside the app, using jmeter -n … -R.

6. Report on results

Partly

Good live numbers. Nothing for looking at saved results or making the report.

  • Live and after the run: tiles for samples, rate, average, 95th percentile, errors and users, plus four charts. A list of failed requests, a per-request table and JMeter's own output.
  • Failed requests show only the code and message. You cannot see what was sent or returned, which is the first thing needed to find out why a request failed.
  • The per-request table has samples, average, minimum, maximum and three percentiles, but no Total row. At the default panel size only the first rows are visible.
  • History lists earlier runs. There is no way to open a results file from somewhere else, or to compare two runs.
  • No HTML report. The app does not make or open the dashboard.
Quick win

The results file our app saves is in the format the HTML report needs. We ran jmeter -g results.jtl -o report on a run saved by our app and it produced a full report. A "Generate report" button could call exactly that.

Very large plans freeze the window

Medium

What happens. Opening a plan with a few thousand requests is fast. Opening a plan with tens of thousands makes the window stop responding. The time grows faster than the size of the plan.

Requests in the planFile sizeTime to open
500195 KB0.8 s
2,000766 KB1.0 s
5,0001.9 MB1.7 s
15,0005.7 MB11.5 s
40,00015 MBNo answer after 60 s. Windows reported "Not responding".

Why it matters. Plans this large are unusual, but generated or heavily recorded plans can reach them. Three times the plan took more than six times as long.

Suggested fix. Find the step that grows faster than the plan, and load plans in the background with a progress message so the window stays alive.

Users tile shows 1 after a finished run

Low

What happens. During the run the tile counts up correctly to 9. When the run finishes it shows 1 and the chart ends at 1, although 10 users ran and none are left.

Suggested fix. Show 0 when the run has finished, and the peak if you want a summary.

Per-request table is cut off and has no total

Low

What happens. On the Requests tab, only the first few rows fit at the default panel height and the last row is cut off. There is no Total row, which JMeter's Summary Report has.

Suggested fix. Make the table scroll, pin the header, and add a Total row.

Settings that come from defaults are invisible

Low

What happens. The example plan sets the server and port once in HTTP Request Defaults. In each request, the Server and Port boxes are empty, so nothing says which server the request will call. JMeter's window behaves the same way.

Suggested fix. Show the inherited value as grey placeholder text, such as "127.0.0.1 from HTTP Request Defaults".

"No matches" does not point to add mode

Low

What happens. The palette searches existing elements and commands. Typing json to add a JSON Extractor shows "No matches". Adding needs the + prefix, which is only hinted at in the footer.

Suggested fix. When a search finds nothing, offer "Add an element named json?" and list matching element types.

Long element names are cut off without a sign

Low

What happens. In the tree, an assertion named "Page has the form" shows as "Page has" next to its grey type label. There is no ellipsis and no tooltip.

Suggested fix. Add an ellipsis and show the full name and type in a tooltip.

Form scroll position carries over to the next element

Low

What happens. After scrolling down a long request form, selecting another request opens it at the same scrolled position instead of at the top.

Suggested fix. Return to the top when another element is selected, and remember the position only for the same element.

Suggested order of work

A proposal, not a commitment. The order puts first what lets a person finish a whole test inside the app.

The idea behind the order

A test engineer's day is: get a script, fix it, run it, find out why it failed, report. Today our app does the middle well. Two ends are missing, getting a script in and getting answers out. That is why the first three steps below are the ones to do first.

  1. See what failed. High Add a request and response viewer for failed requests, built from the run's results. It turns "100 errors" into "100 errors, here is why".
  2. Reuse and start. High Add File > New, copy, cut and paste, and a multi-line editor for request bodies and scripts. These remove the most daily friction.
  3. Open results and make the report. High Open a saved results file, and add a button that makes and opens the HTML report. The files are already compatible.
  4. Make correlation faster. High An expression tester with a pasted or recorded response. Add variable values after a validate.
  5. Get a script from a browser. High The recorder, then templates and import from cURL. This is the biggest piece of work, so it comes after the quick wins.
  6. Fix the small problems. Low The seven items on Problems found, apart from the large-plan one, are each small and can be done as part of the steps above.
  7. Handle very large plans. Medium Find what makes opening slow and keep the window responsive.
  8. Everything else. Medium Properties and -J overrides, comparing runs, distributed testing, per-request graphs.
Tip

Each of these can be checked the same way this guide did it: repeat the task with the example plan and compare with Apache JMeter. The example in docs/guide/demo is built so that the right answer is known: 500 requests, 100 errors, and no cart failures.

Sources and method

What we read, how we tested, and what the tests did not cover.

How we tested

  1. We started the example web shop and confirmed from the command line that the example plan gives 500 requests and 100 errors.
  2. We opened the plan in the real Apache JMeter 5.6.3 window, clicked through each task and took screenshots of every window and menu.
  3. We built our JMeter UI from the main branch (release profile) and repeated each task with the same plan.
  4. For the performance numbers we generated plans of 500 to 40,000 requests and timed how long the window took to show the plan.
  5. We checked that the results file from our app can be turned into an HTML report by JMeter.

What we did not cover

  • Recording and distributed tests in our app, because the features do not exist yet. In Apache JMeter we only looked at the recorder form and the Remote menu. We did not record a site or start workers.
  • Linux and macOS by hand. All screenshots and timings are from Windows. The automated tests of the app run on Windows, Linux and macOS for every change, but nobody has used the window by hand on Linux or macOS yet.
  • Accessibility. We did not test with a screen reader.
  • Plugins and JMeter versions other than 5.6.3.
  • Timings come from one run on one machine. Use them to compare sizes, not as exact figures.
